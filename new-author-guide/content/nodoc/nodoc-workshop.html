Introduction · NoDoc platformWorkshop orientation

NoDoc is an Oracle APEX documentation workbench for creating, organizing, reviewing, improving, ingesting, and preparing technical content for publication. This workshop follows the LiveLabs author journey: select the right Focus Area, create an article and version, build focused pages, review changes, validate the preview, then use the existing WMS publishing request path.

Prerequisites

  • Oracle SSO access to the NoDoc environment.
  • A NoDoc role: CONTRIBUTOR for authoring or READER for review-only activities.
  • The assigned LiveLabs Focus Area and approved source material for the workshop.
Role and ownership determine the actions you see

Use the controls that your current NoDoc role and page ownership allow. A contributor normally creates and maintains owned content; a reader or reviewer comments and drafts where allowed; a page owner approves drafts, creates versions, ingests content, and performs other protected actions. Do not assume an unavailable control is a step you should bypass.

Objectives

  • Navigate NoDoc and select the correct Focus Area.
  • Create an article, version, and page set for a documentation topic.
  • Edit content, apply metadata, and use supported editor features.
  • Collaborate with comments and draft review without overwriting original content accidentally.
  • Apply AI-assisted correction and generate an article information map with explicit human review.
  • Ingest and query approved content with Ask NoDoc while inspecting source context.
  • Complete Quality Assurance and review before creating the WMS publishing request.

Connect to NoDoc, confirm the assigned role, and open the LiveLabs Focus Area used throughout the workshop.

Objectives

  • Sign in through Oracle SSO.
  • Navigate the NoDoc platform.
Task 1 · Reach NoDoc Platform
  1. Open the approved NoDoc environment. Open NoDocRequires Oracle VPN and NoDoc access.
  2. Sign in through Oracle SSO. If the stage environment requests a bypass code, obtain it through the approved manager process; do not paste codes into workshop artifacts.
  3. Choose the NoDoc application.
  4. Confirm that the NoDoc platform opens, then check the role or ownership indicator available in your tenancy. Use a contributor role to author; use a reader or reviewer role only for the review actions it exposes.
Task 2 · Open LiveLabs Focus Area
  1. Open the navigation menu and select LiveLabs Focus Area.
  2. Open the LiveLabs repo in that Focus Area and confirm that its content is visible. In this guide, “LiveLabs repo” means the NoDoc workspace content location; it does not require a local Git workflow.
  3. Use Open All or Close All, if those controls are available, to inspect the article and page hierarchy before adding content.
Task 3 · Understand The Workspace Hierarchy
  1. Use the hierarchy Focus Area → LiveLabs repo → article → article version → page to decide where a change belongs.
  2. Keep a page focused on one concept, task, example, restriction, reference, or error topic. Create another article instead of inventing an unsupported sub-page level.
  3. Work in the assigned LiveLabs Focus Area. Creating, migrating, renaming, or deleting a Focus Area is an owner or administrator action and needs the appropriate content and release approval.
Focus Area administration is not the default LiveLabs author route

The platform can create, rename, delete, and migrate Focus Areas. Use those operations only when the assigned owner or administrator has confirmed the target, source, and recovery path; do not create a parallel Focus Area merely to start a workshop.

Metadata tags: what they are and how to use them

Metadata tags are structured labels that make pages easier to organize, filter, ingest, and find in Ask NoDoc. Add the team-approved tags near the top of each page. Use the current PagesMetaData choices in NoDoc as the authority for values and tag syntax; do not invent a value simply because a tag name exists.

  1. Open the current page's metadata control or the available PagesMetaData reference.
  2. Select the tags that describe the page and use the exact approved values for the selected Focus Area.
  3. Place the metadata at the top of the page, save, and verify that the rendered page still has the intended title, content, and hierarchy.
  4. After a rename or move, review the metadata again. The content name can change while tag values still need manual correction.

Article metadata and Information Maps

If you will generate an Information Map, reserve the first article page for article-level metadata. Generate the map only after all child pages exist; the documented flow replaces that first page's normal body while preserving its metadata.

Use filter tags only for intentional in-page variants

Filter tags are not metadata tags. They delimit content that applies to a platform, language, product, license, or version so shared content is not duplicated. Define the name with the team, and always provide a matching end marker.

Task 3 · Add Structured Content
  1. Edit Prepare and add a concise introduction, objectives, and prerequisites. Keep the page self-contained so a reader can understand its purpose without opening a second page.
  2. Use headings and a numbered procedure for the learner sequence. Use a note or block quote only when it adds a warning, decision, limitation, or context that should not be buried in a task.
  3. Add a code block only for content the learner can use. Select the applicable language when the editor offers it, explain how to run it and validate the result, and never include secrets or unverified commands.
  4. For a cross-reference, copy the target page's Relative Path, select the link text in edit mode, use the link control, paste the relative path, save, and test the result in view mode.
  5. Use supported images with descriptive alt text. Use Markdown source mode, when available, to inspect the generated structure; then review the rendered page as the learner will see it.
  6. Use a FreeSQL block only when that control is available and the workshop genuinely needs verified runnable database practice. It is not a substitute for explaining the expected result and validation.
  7. Save the page and verify its title, metadata, TOC position, links, images, and rendered content.
Expected result

The Prepare, Author, and Review pages are visible in the intended order, each has a distinct purpose, and their metadata and relative links match the current article version.

Task 4 · Maintain Structure, Links, And Versions
  1. To rename an article or page, select it in the TOC and use Edit Name. Review the metadata values afterwards; a rename can leave tag values that still need manual correction.
  2. Move an article only within the Focus Area and move a page only within its article. Recheck page order, relative links, and the rendered preview after the move.
  3. As the article owner, create a new article version when a substantial update needs an independent content snapshot. Select the article, choose Create Version, enter the agreed label, then make and validate changes in the new version.
  4. Ingest a new version separately after its content is ready; creating the version alone does not make it available to Ask NoDoc.
  5. Use Restore Article Version only as the owner, after confirming the exact target and recovery need. Verify the restored TOC and content before resuming normal edits.
High-impact operations stay role-gated

Deletion, Focus Area migration, direct repository conversion, and legacy pre-publish or push operations are not part of this guide's default LiveLabs author route. Use them only with the owning administrator or release owner, an approved target, and a recovery plan.

Lab 3 · Review And Drafts15 minutes

Use comments for precise feedback and drafts for proposed edits. The original page remains protected until the owner reviews and explicitly overwrites it.

Objectives

  • Add an anchored review comment.
  • Create and inspect a draft.
  • Review differences and apply an owner-approved overwrite.
Draft lifecycle

A non-owner's edit is a draft, not a change to the original. Saving that draft leaves the original intact and notifies the owner where the current environment supports notification. The owner then reviews the difference, accepts or rejects individual changes, approves the reviewed draft, and overwrites the original only when the final change set is correct.

Task 1 · Add A Comment
  1. Open the Prepare page in view or edit mode and select the exact sentence that needs clarification.
  2. Use the comment control to add a specific, actionable suggestion, then save the comment.
  3. Confirm that the comment remains anchored to the selected text. If the environment supports notifications, the page owner receives the comment for follow-up.
  4. Use My Comments, when available, to find assigned comments and reopen the exact page location instead of searching the TOC manually.
Task 2 · Create A Draft
  1. Sign in as a non-owner reviewer, or use the supplied reviewer account, then open the commented page and choose Edit.
  2. Accept the prompt to work on a draft. Do not try to work around the ownership boundary.
  3. Improve the selected sentence, preserve the page's metadata and links, and save the draft.
  4. Confirm that the original page still shows the approved content while the owner has a draft to review.
Task 3 · Review And Approve
  1. Sign in as the page owner and open Drafts to inspect the pending draft.
  2. Open the current difference view, labelled View Diff or Difference depending on the environment, and review every change in context.
  3. Accept or reject changes individually, then approve the reviewed draft.
  4. Overwrite the original only after confirming the final content, metadata, links, and technical meaning.
  5. Reopen the rendered page and resolve or update the related comment so reviewers can see the final decision.
Lab 4 · AI Assistance, Codex Skills, And Information Maps15 minutes

Use NoDoc AI assistance to improve an author-reviewed draft, use available focus-area Codex skills for analysis, then generate an article Information Map only after the page set is complete.

Objectives

  • Run a standards or persona-based AI correction.
  • Inspect differences before overwrite.
  • Run an available focus-area Codex skill on selected content.
  • Generate an information map from the article's first page.
AI creates a proposal, not an approved change

Vibe Doc-ing can apply standards, use a persona or custom prompt, and rewrite selected text. It does not prove technical correctness, policy compliance, or source accuracy. Compare the proposal with the original, reject unsupported wording, and overwrite only after the page owner completes human review.

Task 1 · Run AI Correction Safely
  1. Open the Author page as its owner.
  2. Choose Vibe Doc-ing, then select the action that matches the need: Apply Standards, a supported persona extraction, a custom prompt, or a checklist available in the current UI.
  3. Review the generated content and open the difference view before making any replacement.
  4. Reject unsupported changes. Keep only improvements that preserve the approved technical meaning, required metadata, links, code behavior, and safety or review constraints.
  5. Use Overwrite only after human review, then save and recheck the rendered page.
Task 2 · Try An Inline Correction
  1. Select one sentence on the page.
  2. Right-click and choose Vibe Doc-ing.
  3. Select Formal, Heading, or a custom prompt when that action is available.
  4. Review the result, edit it if needed, and replace only the selected text if it is accurate. Save the page after the change.
Task 3 · Use A Focus-Area Codex Skill
  1. Open the Codex control at the Focus Area level, if your role and tenancy show it.
  2. Use Open All or Close All to choose only the articles and pages that need analysis.
  3. Run only a skill available in that UI. The accessible source material documents a Grade skill that analyzes selected pages and produces recommendations.
  4. Review the result and, when offered, download its CSV report. Treat recommendations as review input; they do not automatically modify the pages.
Task 4 · Generate The Information Map
  1. Confirm that all workshop pages exist and are saved.
  2. Open the first page of the article as the owner. Keep that page to article metadata when you plan to generate an Information Map.
  3. Choose Generate Information Map.
  4. Confirm that NoDoc generates a summary and source link for each child page while the first-page metadata remains intact.
  5. Review the map as an article-level navigation aid for people and retrieval; it does not replace the child pages or their normal Quality Assurance review.
Lab 5 · Ingest And Ask NoDoc15 minutes

Make approved content available to Ask NoDoc, then constrain a question to the right Focus Area, article, and version.

Objectives

  • Ingest a page or article deliberately.
  • Select a focused Ask NoDoc context.
  • Check that answers remain grounded in workshop content.
Ingest before you ask

The author workflow is: save and approve the page or article, ingest the intended scope as its owner, wait for completion, select a narrow Ask NoDoc focus, then inspect the answer and its source context. A newly created article version has its own ingestion state, so update it before relying on it in Ask NoDoc.

Task 1 · Ingest Approved Content
  1. As the owner, confirm that the selected page or article is saved, technically reviewed where required, and safe to make available for retrieval.
  2. Select the exact page or article and choose Ingest. NoDoc chunks and vectorizes that selected content for retrieval.
  3. Wait for the ingestion status to complete, record the scope and timestamp, then ask a question that the ingested content should answer.
  4. If the result is not available, first confirm the selected scope, current version, and completion status. Do not repeatedly ingest or broaden the scope without understanding what changed.
  5. Do not ingest confidential, secret, or unapproved production content into a shared test or authoring flow.
Task 2 · Ask A Focused Question
  1. Open Ask NoDoc from the application menu.
  2. Choose Focus and select NoDoc. Use the unfiltered option only when the wider NoDoc collection is genuinely needed.
  3. Narrow the context in order: Focus Area, article, then release version.
  4. Ask a question answered by the Prepare page.
  5. Inspect the answer and source or link context. Tighten the focus if the answer mixes content from an unintended article or version.
  6. Use the selected-articles or filter indicator, when shown, to inspect or remove active filters before starting an unrelated question.
Task 3 · Use Search Modes And Manage Chat Context
  1. Use MCP (Metatag Command & Processing) only as the Ask NoDoc metadata mode. It is not a Codex MCP content-creation server.
  2. Use Select & Ask to ask a question against pages matching selected metadata. Use Select & Search to generate a /find result list of matching page links.
  3. Use Vibe Searching to describe the product, deployment model, or topic type in natural language when you do not yet know the exact metadata combination.
  4. Use URL focus only for a currently supported, approved Oracle URL and validate the target before asking questions. Use DBSA only when the option is visible and your environment grants access.
  5. Start a new chat when you need a clean context. Chat history can restore previous filters, so recheck the active focus before relying on an older conversation.
  6. Download the current chat JSON only to the approved location and only when it contains no secrets, personal data, or unapproved source material.
Why this guide does not add a Codex MCP-server procedure

Available NoDoc material uses “MCP” in two different ways: the metadata search mode above, and a conceptual Model Context Protocol integration for documentation retrieval. It does not verify a currently deployed Codex MCP server that can write NoDoc content. Follow only the in-product Codex authoring route until product owners publish the current connection, authentication, tool scope, and approval requirements.

Lab 6 · Quality Assurance, Review, And Publishing Request15 minutes

Create the article in NoDoc, copy its current preview link, complete the Quality Assurance checklist, and wait for WMS review. Create the publishing request only after WMS status is Completed.

Objectives

  • Use the NoDoc preview link to check the final article.
  • Complete the Quality Assurance checklist and resolve review comments in NoDoc.
  • Create the WMS publishing request after review is complete.
NoDoc checks and WMS checks have different roles

Use NoDoc to check the article, metadata, page order, links, and current preview. Use WMS to record the Self Quality Assurance checklist, status, review outcome, and publishing request. Follow the shared Review & Publish walkthrough for the WMS controls instead of creating a separate handoff document.

Task 1 · Check The NoDoc Article
  1. Confirm metadata, page order, links, code blocks, images and alt text, and rendered content in the current NoDoc preview.
  2. Copy the preview link and add it to the Self Quality Assurance checklist.
  3. Save the checklist and move the workshop to Self Quality Assurance Complete.
Task 2 · Wait For Review
  1. Wait for WMS review rather than creating a separate review document.
  2. Resolve requested changes in NoDoc, update the preview link if needed, and repeat the Quality Assurance checks.
  3. Continue only when the reviewer has moved the WMS status to Completed.
Task 3 · Create The Publishing Request
  1. In WMS, open Publishing and click Publish to LiveLabs.
  2. Enter the approved production location for the final workshop instructions, choose the required publishing options, and create the request.
  3. Save and confirm Publish Requested. Configure Sandbox Environment only when the workshop needs a LiveLabs sandbox.
